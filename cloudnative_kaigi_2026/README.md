**タイトル: 継続的な負荷検証を目指して**

**主張したいこと:**

継続的に開発されているサービスにおいて、すべてのエンドポイントを網羅した負荷検証シナリオを人手でメンテナンスし続けることは現実的ではない。AIに「人間がやるのと同じ手順」でシナリオを作らせることで、実際のトラフィックをもとにした負荷検証を継続的に維持できるようにした事例を紹介する。

## はじめに

サービスを継続的に運用するにあたり、定期的な負荷検証は非常に重要な取り組みである。たった数行の追加コードが、N+1クエリを生んでサービスダウンを引き起こすこともある。しかし、継続的に開発されているサービスでは常に新しいコードが生まれ続け、そのすべてに対して負荷検証シナリオを開発し続けることは容易ではない。

本セッションでは、この課題に対してAIを活用して解決した事例を紹介し、継続的に負荷検証ができる状態を作るための仕組みについて共有する。

## 2025年末のサービスダウン

### 何が起きたか

2025年の年末、私たちのサービスは約1時間にわたってダウンした。

障害発生時にはすでに負荷検証を実施していたが、エラーが発生していたのは負荷検証の対象に含まれていないエンドポイントだった。そのエンドポイントは平常時はそれほど高い負荷がかかるものではなかった。しかし年末という時期に大量のアクセスが集中した結果、READクエリがプライマリDBに大量に発行されることや、DBトランザクションの中の処理で外部APIをコールする処理などが重なり、ロック時間が長くなってサービスがダウンしてしまった。

### 障害の構造

この障害には2つの側面がある。

1つ目は、負荷検証の網羅性の問題である。負荷をかけていたエンドポイントはきちんと問題なく動作していたが、対象外のエンドポイントが落とし穴になった。「やっていた」と「すべてをカバーしていた」の間には大きな差がある。

2つ目は、平常時には問題が表れないコードの問題である。

READクエリがプライマリに向いていた原因は、私たちの実装の問題だった。レプリカに向けるべきクエリがプライマリに向いたままになっていたほか、GORMのauto reloadにより主要なテーブルのリレーションが大量に読み込まれていた。さらに、トランザクション内で外部APIを呼び出していたことで、1トランザクションあたりのロック保持時間が伸びていた。平常時はリクエスト数が少ないため問題にならないが、大量アクセスが重なると「長いロック × 多数の同時リクエスト」が掛け算で悪化する。

加えて、DBはパフォーマンスが悪化すると芋蔓式に連鎖する特性がある。ロック待ちが増えると接続プールが枯渇し、接続待ちのリクエストがさらに積み上がり、タイムアウトが多発してエラーレートが急騰する。あるラインを超えると一気に崩壊するため、「少し遅くなっている」段階で気づくことが難しく、気づいたときにはすでにダウンしているという状況になりやすい。こうした問題は平常負荷では顕在化しにくく、負荷検証をしない限り気づけない類の問題だった。

### 学びと方針転換

この障害の学びは明確だった。「実際のトラフィックを元に負荷シナリオを作り、継続的にメンテナンスできる仕組みを作る」ことが必要だということだ。

従来は、開発者が手動でシナリオを書いて管理していた。新しいエンドポイントが追加されても、負荷検証シナリオがそれに追随するかどうかは開発者の意識次第であり、抜け漏れが発生しやすい状況だった。

## 継続的な負荷検証の課題

### シナリオのメンテナンスコスト

負荷検証ツールを使ったシナリオ作成自体は難しくない。問題はそれを継続的に維持し続けることだ。

新しいエンドポイントが追加されるたびにシナリオを書く。既存のAPIのパラメータが変わればシナリオを更新する。認証フローが変わればシナリオ全体を見直す。こうした作業が積み重なることで、シナリオのメンテナンスは徐々に後回しになっていく。

### 網羅性の担保

どのエンドポイントが重要で、どのエンドポイントに負荷をかけるべきかを判断するのも容易ではない。特に「平常時は負荷が低いが、大量アクセスで問題が顕在化するエンドポイント」は見落とされやすい。

開発者の感覚だけに頼るのではなく、実際のトラフィックデータをもとに重要なエンドポイントを自動的に発見できる仕組みが必要だった。

## AIを活用した解決アプローチ

### 人間がシナリオを作るときの手順

まず、人間のエンジニアが負荷検証シナリオを新しく追加するときの手順を整理する。

1. Grafana LokiなどでAPIのアクセスログを確認し、どのエンドポイントがどのような順序・頻度で呼ばれているかを把握する
2. そのパターンをもとにシナリオのコードを書く
3. 開発環境でシナリオを実際に実行して動作確認する
4. 失敗したらログやレスポンスを確認して修正する
5. 安定して動くことを確認したら本番の負荷検証に組み込む

この手順は当たり前のものに見えるが、逆に言えば「この手順をAIにそのままやらせればよい」という発想が今回のアプローチの出発点になった。

### runnとは

今回のシナリオ実行に使っているrunnはk1LoW氏が開発しているOSSのAPIシナリオテストツールだ。シナリオをYAML（runbook）で記述し、HTTPリクエストを順番に実行できる。変数の受け渡し、ループによるポーリング、レスポンスの条件チェックなどが宣言的に書けるのが特徴で、GoライブラリとしてもCLIとしても使える。

シナリオの構造はシンプルで、以下のようなイメージだ。

```yaml
desc: 検索→詳細取得フロー
steps:
  login:
    include: setup_user.yml        # 認証などの共通処理をinclude
  search:
    req:
      /v1/items/search:
        get:
          headers:
            Authorization: "Bearer {{ steps.login.token }}"
          params:
            query: "{{ vars.keyword }}"
    test: current.res.status == 200
  wait_for_ready:
    loop:
      count: 5
      interval: 3s
      until: current.res.body.status == "ready"
    req:
      /v1/items/{{ steps.search.res.body.id }}:
        get:
          headers:
            Authorization: "Bearer {{ steps.login.token }}"
```

ステップ間でレスポンスの値を参照できるため、「ログイン→リソース作成→IDを使って操作」といった状態を持つAPIフローを自然に表現できる。

### 仕組みの全体像

2つのスキルがそれぞれ人間の作業フローのフェーズを担う形になっている。

```
本番Loki
  ↓ MCPで直接クエリ
[extract-scenariosスキル]
  ログを分析してAPIパターンを発見
  ↓ 既存シナリオとの重複チェック
  ↓ 人間が候補を承認
  runbook YAML を生成
  ↓
[run-stressスキル]
  dev環境で3回連続実行
  失敗→ログ確認→修正→再実行
  ↓
  dev Lokiでリクエスト到達を確認
  ↓
  stress.yml に登録
  ↓
継続的な負荷検証へ
```

### Claude Codeスキルによる実装

今回の仕組みはClaude Codeのスキル機能を使って実装している。スキルとは、AIに特定のツールと手順書を与えて特定のタスクをこなせるようにする仕組みだ。

#### extract-scenariosスキル: ログを読んでシナリオを書く

このスキルでは、AIにGrafana LokiへのアクセスをMCP経由で与えている。AIは本番環境のLokiに直接クエリを投げて実際のアクセスログを取得し、ユーザーやドライバーがどのAPIをどんな順番で呼んでいるかを分析する。

Lokiへのクエリは例えば以下のようなものだ。

```
# 外部からの着信リクエストだけを取り出す
{app="<your-app>", container="istio-proxy"} |= `inbound` | json | path != ""

# 特定のエンドポイントを深堀り
{app="<your-app>", container="istio-proxy"} |= `inbound` |= `orders` | json

# 特定ユーザーの一連のリクエストを時系列で追跡
{app="<your-app>", container="istio-proxy"} |= `inbound` |= `:<user_id>:` | json
```

AIはこうしたクエリを自分で組み立てて投げ、エンドポイントのパターン・呼び出し順・頻度を把握する。普段は少ないが特定の条件下で急増するエンドポイントなども、ログから自力で発見する。

発見したパターンをもとにrunbook YAMLを生成し、既存シナリオとの重複チェックも行って、新規性のあるシナリオ候補のみを人間に提案する。シナリオ作成に進む前に必ず人間の承認を取るステップを設けている。

#### run-stressスキル: dev環境で実際に実行して確認する

シナリオを書いたら終わりではない。このスキルでは、AIがdev環境で実際にシナリオを動かす。内部的にはrunnをGoライブラリとして組み込んだ `stress-runner` というCLIを使い、次のように実行する。

```bash
./bin/stress-runner run runbooks/templates/<scenario>.yml
```

重要なのは、1回動いたら完了ではなく、3回連続で成功するまで繰り返すという規約だ。タイミング依存のバグは1回の実行では見つからないことが多い。失敗した場合はレスポンスのHTTPステータスコードとボディを確認し、ポーリングの間隔や回数を調整するなどして修正を加え、再度検証する。

さらに、dev環境のLokiにもクエリを投げて、リクエストがAPIサーバに実際に届いているかを確認するステップも含まれている。シナリオが動いているように見えてもリクエストが届いていないというケースをLoki側で検証することで、より確実な動作確認ができる。

### テスト環境の設計

シナリオの品質だけでなく、テスト環境の設計も負荷検証の精度に直結する。

まず、テストに使うデータは本番相当の量を用意している。データ量が少ないとインデックスが効きすぎて本番では起きないほど速く応答してしまったり、逆にロック競合が再現しないといった問題が生じる。本番に近い規模のデータがあることで、初めて本番に近い挙動が再現できる。

次に、テスト実行時の外部サービスへの通信はすべてモックしている。本番環境では決済や通知など外部APIと連携しているが、負荷検証の目的はあくまでも自分たちのサービスのボトルネックを見つけることだ。外部APIの応答速度に結果が左右されないよう、外部通信はスタブに差し替えることで、計測対象を自分たちのコードに絞っている。

また、テストに使うユーザーデータやドライバーデータは配車数の多いものを選んでいる。配車数が多いということは関連するデータのリレーションが多く、クエリの負荷が高くなりやすい。意図的に「重い」データを使うことで、平常時には見えないN+1や遅いクエリが顕在化しやすくなる。このデータの選択もDBから自動的に取得する仕組みにしており、常に最新の本番相当データを使って検証できる状態を保っている。

### さも人がやるかのように

このアプローチのユニークな点は、AIが「ログを見る→シナリオを書く→実際に動かして確認する→失敗したら直す」という、人間のエンジニアがやるのとまったく同じ手順を踏んでいることだ。

AIに「シナリオを生成してください」と指示するだけでなく、ログを見る権限と実行する権限を与えることで、AIが自律的にPDCAを回せるようになっている。生成したコードが動くかどうかを自分で確認し、動かなければ自分で直す。人間がレビューするのはAIが「動作確認済み」と判断したシナリオだけでよく、大幅に手間が減る。

## 運用してみてわかったこと

### カバレッジの向上

仕組みを導入する前は、明示的にシナリオを書いていたエンドポイントしか検証できていなかった。導入後は実トラフィックベースでシナリオが追加されるため、開発者が見落としていたエンドポイントにもカバレッジが広がった。

特に、「平常時は負荷が低いが大量アクセスで問題が顕在化するエンドポイント」はまさに今回の障害の教訓そのものだ。AIがLokiを眺めて「このエンドポイント、意外とアクセスがあるな」と気づくことで、人間の思い込みによる見落としを防げるようになった。

### スキルという設計の重要性

単にAIにシナリオ生成を依頼するだけでは、品質のばらつきが大きく実用に耐えなかった。スキルとして手順書とツールをセットで定義することで、AIが毎回同じ品質で作業できるようになった。

特に「3回連続成功」という規約をスキルに組み込んだことは大きかった。この規約がなければ、AIは1回動いただけで完了と判断してしまう。人間が経験則として知っている「1回成功しても信用するな」というノウハウをスキルに落とし込むことで、AIの出力品質を担保できた。

### 人間のレビューが残る部分

完全自動化を目指したわけではなく、AIが提案したシナリオ候補を人間が承認するステップを意図的に残している。特に複数のAPIを複雑に連携させるシナリオや、本番データの特性に依存する部分は、AIが見落としやすい。

AIが「動く」シナリオを作ることはできるが、「ビジネス的に意味のある負荷パターンになっているか」という判断は人間が行う。AIと人間の役割分担を明確にしたことで、全体として品質と効率のバランスが取れた。

## まとめ

継続的に開発されているサービスで負荷検証を継続的に実施するためには、シナリオのメンテナンスを人力だけに頼らない仕組みが必要だ。

今回のアプローチのポイントは、AIに「生成する」だけでなく「確認する」権限も与えたことだ。LokiへのアクセスとBashの実行を組み合わせることで、AIが人間と同じ手順でシナリオの動作確認まで完結できるようになった。

AIに何かを任せるときは、人間がその作業をどうやっているかを分解し、その手順とツールをそのままAIに渡すことが重要だと感じている。「AIが自動生成する」という発想より、「AIが人間の代わりに手順を踏む」という発想のほうが、実用的な品質につながった。

今回の障害で得た「やっていた」と「すべてをカバーしていた」は別物だという教訓を、仕組みで解決できたことが今回の一番の学びだ。
